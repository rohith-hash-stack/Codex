**Canonical interpretation of TAD §9's `health_status`/`availability` (approved 2026-08-30, D1 review):** TAD §9 lists these as two flat, undistinguished attributes. Resolved as: `health_status` (`ProviderHealthStatus`: `HEALTHY`/`DEGRADED`/`UNHEALTHY`/`UNKNOWN`) is the operational condition of the provider itself; `availability(capability, repository) -> float` in `[0.0, 1.0]` is whether the provider is currently usable for a *specific capability* in a *specific repository/environment* — an adapter-reported fact, not an aggregated selection score (that aggregation is D2's job, per TAD §10/§31). The two are structurally independent: nothing in the contract derives one from the other, and `test_healthy_provider_can_report_zero_availability`/`test_unhealthy_provider_can_report_nonzero_availability` prove a HEALTHY provider can report 0.0 availability (e.g. missing license for this repository) and an UNHEALTHY one can still report full availability. ## I. ADR-018 — Provider Scoring Factor Sourcing — RESOLVED 2026-08-30

**Status: RESOLVED.** Originally raised as a finding during D2 implementation (original writeup preserved below, unmodified, for the audit trail); closed by explicit architecture decision during D2 review. `CapabilityRegistry` and its tests were refactored to match — see the updated contract in "Resolution" below.

### Resolution

| Factor | Origin (final) |
|---|---|
| `capability_match` | Registry-derived: `1.0` for any provider `providers_for()` returns (it declares the capability), and such a provider is the only kind ever scored — non-declaring providers are excluded before scoring, never scored at `0.0`. |
| `availability` | Registry-derived: `adapter.availability(capability, repository)` (D1), read fresh on every `evaluate()`/`rank()` call. |
| `evidence_quality` | **Supplied metadata**, not computed: `ProviderScoreProfile.evidence_quality`, attached once via `CapabilityRegistry.register(adapter, profile)` — canonical per-provider configuration, not a per-query input. Pydantic-validated to `[0.0, 1.0]`. |
| `cost_factor` | **Supplied metadata**, same mechanism: `ProviderScoreProfile.cost_factor`, already normalized `[0.0, 1.0]` by whoever configures the profile — never a raw monetary value. |
| `freshness` | Registry-derived from the adapter's own `freshness` timestamp (D1) via `codex.registry.scoring.default_freshness_score()` — a single generic (provider-neutral) exponential decay with a documented, swappable half-life (`DEFAULT_FRESHNESS_HALF_LIFE`, 24h). Explicitly a calibration point (see below), not a claimed-final algorithm. |

**Why a profile, not per-call arguments:** the original D2 implementation required `rank()` callers to supply `evidence_quality`/`freshness_score`/`cost_factor` as dict arguments on every call — functionally correct (nothing was invented) but architecturally wrong, because two different callers could supply different values for the same provider/capability/repository and get different rankings. `ProviderScoreProfile` is now attached once at `register()` time (registry-owned state), so `rank(capability, repository)` — no scoring kwargs at all — is deterministic for a given repository regardless of caller. `test_ranking_does_not_depend_on_caller_supplied_scoring_values` proves the old signature is gone (calling with the removed kwargs raises `TypeError`).

**`evidence_quality`/`cost_factor` remain explicitly unresolved *sourcing policy*, by design:** ADR-018 decides *where the registry looks* (a profile attached at registration), not *how a real value gets computed* for a real provider (SCIP, CodeQL, ...) — that remains an open extension/calibration point, deliberately not decided in D2 per the directive's explicit instruction not to invent a universal quality formula or cost normalization. A provider registered without a profile is fully usable for discovery/evaluation (`providers_for()`, `evaluate()`); `rank()` raises a clear `ValueError` naming it if asked to score it, rather than guessing.

**Final `rank()` contract:**

```python
def rank(
    self, capability: Capability, repository: RepositoryMetadata, *, now: datetime | None = None
) -> list[ProviderEvaluation]: ...
```

`now` is accepted only to make freshness decay deterministic in tests; real callers omit it. No other parameters — this is the structural guarantee behind "ranking does not depend on arbitrary caller-provided scoring values."

**No cross-document contradiction found.** TAD §31 gives the aggregation weights and normalization requirement but never defined individual-factor sourcing; this decision fills that gap without changing the formula, the weights, the `capability_match=0` exclusion rule, or anything in the (still-untouched, still-approved) D1 `ProviderAdapter` contract. Provider-independence, eligibility-vs-availability separation, and deterministic tie-broken ordering are all unchanged and re-verified by the updated test suite.

### Original finding (2026-08-30, preserved for the audit trail)

Discovered while implementing D2 (`CapabilityRegistry.rank()`). Not silently resolved — flagged here per the Phase D directive's own instruction ("if D2 exposes an underspecified behavior that cannot be resolved from HLRD/TAD/reconciliation/resources, STOP and report it").

TAD §31 defines the `ProviderScore` aggregation:

```
ProviderScore =
    0.40 capability_match
  + 0.20 evidence_quality
  + 0.15 availability
  + 0.15 freshness
  + 0.10 cost_factor
```

...and states each factor is normalized to `[0.0, 1.0]`, with `capability_match = 0` excluding a provider before scoring. It does **not** define how any individual factor is computed — that was always going to be down to whatever implements the registry. D1 (already approved and closed) resolved two of the five:

| Factor | Source | Status |
|---|---|---|
| `capability_match` | `capability in adapter.supported_capabilities` — 1.0 if the provider is a candidate at all (it's never scored otherwise), 0.0 (excluded) otherwise | **Resolved**, derivable from D1 |
| `availability` | `adapter.availability(capability, repository)` — already `[0.0, 1.0]` per the D1 clarification | **Resolved**, direct D1 property |
| `evidence_quality` | — | **No source.** No adapter property, no formula in HLRD/TAD, no mention in the reconciliation docs. `Evidence.confidence` is per-*evidence-record* and only exists after extraction — it can't inform a pre-extraction provider-selection score for a query that hasn't retrieved anything yet, at least not without a historical/telemetry aggregation mechanism that doesn't exist yet (Telemetry Store, TAD §65, is itself `NOT_IMPLEMENTED`). |
| `freshness` (as a score) | — | **Half-resolved.** The *raw signal* exists (`adapter.freshness -> datetime \| None`, D1), but converting a timestamp into a `[0,1]` score needs a staleness/decay policy (how many hours/days maps to what score?) that is defined nowhere. |
| `cost_factor` | — | **No source.** No adapter property, no formula. TAD/HLRD mention "cost" only as this weighted factor name; an earlier turn's own guidance ("do not allow cost expressed in raw currency to contaminate the score") implies it should already be pre-normalized before use, but never says by whom or how. |

**What D2 does about it:** implements the formula and weights exactly as specified (`codex.registry.scoring`, tested independently of the registry in `test_provider_scoring.py`), and implements everything the registry *can* determine on its own (registration, capability discovery, eligibility/health/availability evaluation and classification). For the three unresolved factors, `CapabilityRegistry.rank()` requires them as **explicit, required, per-provider-name keyword arguments with no default** — calling `rank()` without an entry for every usable candidate raises `ValueError` naming the provider. Nothing in `codex.registry` guesses a number for any of the three.

**Two candidate resolutions, neither decided here:**
1. Extend the (already-approved) `ProviderAdapter` contract with `evidence_quality`/`cost_factor` properties (mirroring how `health_status`/`availability`/`freshness` already work) — plausible since TAD §9's own attribute list already established the pattern of adapters reporting simple facts about themselves.
2. Treat these as Telemetry/Offline-Calibration concerns (TAD §59, §65-66) — historical per-provider statistics computed from accumulated production evidence, fed into `rank()` by whatever calls the registry (a future D3+ Planner), rather than adapter-reported.

This does not block D3 (Git Adapter): `providers_for()`/`evaluate()`/registration work fully without it, and `rank()` is usable today by any caller (including future D3+ code) willing to supply the three inputs explicitly, exactly as the D2 tests do.

## L. SourceLocation Contract Closure — 2026-08-31

Per the post-D7 directive's Phase A. Closes the one AMBIGUITY §J flagged (SCIP Item "Range boundary convention").

**Inspection performed before coding:** grepped HLRD.md and TAD.md for `SourceLocation` (zero matches — the type name itself appears nowhere) and for "source location"/"line number"/"column" (TAD §12 lists it as a `RepositorySymbol` field and TAD §71's traceability diagram names it as the last link in the evidence chain; HLRD only lists "source locations" as one of several things SCIP *may* provide). **Neither document ever states a numbering or boundary convention** — confirmed not a contradiction (nothing to reconcile), a genuine silent gap. Inspected every current populator: `SCIPAdapter._location_from_range` (the only code path that sets `RepositorySymbol.source_location`, confirmed by `grep -r source_location src/`); `GitAdapter` (no location data at all — `HISTORY` is a whole-file lifecycle fact); `CodeQLAdapter` (uses SARIF `region.startLine` internally, for codeFlow endpoint matching only — never attaches a `SourceLocation` to any entity, confirmed by inspection of `_resolve_location`/`_flow_endpoints`). Re-fetched the authoritative OASIS SARIF 2.1.0 schema's `region` definition directly to confirm its convention rather than assume it: `startLine`/`startColumn`/`endLine`/`endColumn` are all **1-based** (`"minimum": 1`), `endLine` is documented as *inclusive* ("the line number of the last character in the region"), and `endColumn` is documented as *exclusive* ("the column number of the character following the end of the region") — structurally the same half-open-at-the-end model SCIP already uses, offset by exactly 1 on all four numbers.

**Resolved as a specification clarification, not an ADR** (directive Phase A §6): no competing designs or tradeoffs exist to decide between — SCIP (the only current populator) already emits one specific, spec-derived convention, and adopting it as the canonical one requires no behavior change to any existing adapter. TAD §12 amended in place with an inline clarifying note (see TAD's own amendment log); no HLRD change was needed (HLRD never attempted to define a convention).

**Canonical convention:** 0-based, half-open (`[start, end)`), matching SCIP/LSP/tree-sitter. `start_column`/`end_column` optional together, never independently (a location may be line-only). No in-type "whole file"/"unknown" sentinel — `RepositorySymbol.source_location = None` already serves that purpose (used today for `EXTERNAL_LIBRARY` entities). `file_path` is repository-root-relative, `/`-separated, matching `build_canonical_id`'s `qualified_name` convention. `repository_id`/`revision` deliberately excluded from the type itself (always inherited from the containing `RepositorySymbol` — adding them would invent redundant, driftable state).

**Code change:** `codex.ontology.entities.SourceLocation` gained field-level bounds (`start_line`/`end_line`/`start_column`/`end_column` all `ge=0`, via pydantic `Field`) and a `model_validator` enforcing `end_line >= start_line`, both columns present-or-absent together, and `end_column >= start_column` when `start_line == end_line`. This tightens a previously fully-unvalidated type into a deterministic contract without changing any existing adapter's behavior — confirmed by all 275 pre-existing tests (including all SCIP tests, whose real-fixture-derived `SourceLocation` values already satisfy the new constraints) passing unmodified. No provider adapter code was changed — SCIP was already conformant by construction; CodeQL and Git don't currently populate this field at all, so there was nothing to convert yet, only a documented conversion rule for when a future capability does.

**Tests:** 12 new tests in `tests/test_source_location.py` — line-only validity, full-precision validity, zero-width (empty) range validity, multi-line ranges (no cross-line column-ordering constraint), rejection of `end_line < start_line`, rejection of `end_column < start_column` on the same line, rejection of partial column precision, rejection of negative coordinates (parametrized across all four fields), and deterministic structural equality for identical inputs. 287 tests total project-wide, 100% coverage on `codex/ontology/entities.py`, clean ruff/mypy.

**Cross-document effects checked (directive Phase A §6):** Entity Resolution (not yet built — will consume `SourceLocation` only as a tie-breaking/corroboration signal per Phase B below, never as primary identity); Evidence (does **not** carry a `SourceLocation` field at all — confirmed by inspection of `codex.evidence.model.Evidence`, which has `raw_reference` but no location field, so this closure has no direct effect there); `raw_reference` (a separate, already-closed URI-scheme contract, unaffected); source-context retrieval/Verification (both `NOT_IMPLEMENTED`, no effect yet); historical graph queries/`graph_version` (unaffected — `SourceLocation` carries no version-dependent state beyond what its containing `RepositorySymbol` already versions). No genuine architectural decision requiring a STOP was found.

## M. Entity Resolution — 2026-08-31

Per the post-D7 directive's Phase B. TAD component #7 ("Entity Resolution + Reconciliation Engine") is split into two directive phases; this section covers Entity Resolution only (§N covers Reconciliation).

**Pre-audit findings (directive Phase B §7), from direct inspection of `build_canonical_id`, `RepositorySymbol`, and all three provider adapters — not assumed from prior reports:**

- `FILE` is the **only** base type every current provider can produce: `GitAdapter`, `SCIPAdapter` (file references), and `CodeQLAdapter` all call `build_canonical_id(..., base_type=BaseEntityType.FILE, ...)`. Non-FILE (CLASS/METHOD/...) entities come from `SCIPAdapter` alone — "cross-provider symbol convergence" (directive §12) has no live case with the current three providers; recorded honestly as such rather than exercised with a fabricated second symbol-producing provider.
- `build_canonical_id` already gives *exact* convergence for byte-identical inputs (proven by existing D3/D5/D6 tests). The real, previously undemonstrated risk: each adapter derives its FILE `qualified_name` from its own provider format (`git`'s diff output; SCIP's `Document.relative_path`; SARIF's `artifactLocation.uri`, typed as an open `uri-reference` by the OASIS schema — nothing requires it to already be a bare, repo-relative string). Real fixtures inspected in this and prior phases are all already-canonical plain relative paths (no live defect observed), but nothing previously enforced this.
- `RepositorySymbol.provider_ids` (TAD's own field) is populated only by `GitAdapter` (`{"git": path}`) today; SCIP/CodeQL never set it — sparse, not a defect, but merge logic must not drop it.
- **A real, previously undiscovered defect found by this audit**: `IngestionPipeline._commit_entities` (D4) kept only the *last-committed* `RepositorySymbol` per `canonical_id` on a collision — silently discarding an earlier provider's `roles`/`provider_ids` contribution, directly contradicting D4's own documented "no evidence is ever discarded" invariant (`codex/ingestion/pipeline.py`'s own module docstring). Never triggered by any existing test (no two providers previously produced a colliding `canonical_id` in any test scenario), so it shipped unnoticed through D4-D6's own review passes. Fixed as part of this phase (see below) — this is the "concrete conformance defect" that justifies touching D4's `_commit_entities`/`_commit_relationships`, per the directive's own "unless an actual conformance defect is discovered" carve-out (directive top matter, and §25).

**Design (directive Phase B §8-11):** `codex.resolution.entity_resolver.resolve_entities()` — deterministic, no LLM/SLM/embeddings/fuzzy matching, no second identity system. Two match classes only:

1. **`EXACT_CANONICAL_ID`** — two provider entities already share a `canonical_id` (byte-identical inputs). → MERGE.
2. **`NORMALIZED_PATH_IDENTITY`** — a FILE/DIRECTORY entity's `qualified_name`, run through a new `codex.resolution.paths.normalize_repo_relative_path()` (strips `\`→`/`, leading `./`, leading `/`, collapses `//`), recomputes to a *different* `canonical_id` than another entity already holds. → MERGE, with the **recomputed, normalized** id as the definitive canonical id (never whichever raw entity happened to sort first — order-independence proven by a dedicated test). Non-path-shaped entities (SCIP symbols, `EXTERNAL_LIBRARY` package identities) are never renormalized — their own provider-computed id is trusted as-is, per "only use signals the architecture already supports."

No **ambiguous-match** or **conflicting-identity** case exists in the current three-provider set: `canonical_id` already includes `base_type`/`qualified_name`/`revision` in its hash, so two genuinely different entities (different name, different namespace, different revision, different base type) can never collide, and two entities that DO collide are, by construction, the same real entity — there is no case where the current deterministic signals produce a genuine ambiguity. This is recorded honestly as "structurally prevented, not yet exercised," not assumed to generalize to future providers without re-auditing.

**Merge semantics (directive Phase B §10, provenance-preserving):** `roles` — union, order-preserving, deduplicated. `provider_ids` — dict union (a real key collision with different values would be a genuine conflicting-identity signal; none currently possible since each provider uses its own provider-name key). `lifecycle_status` — a non-default (DELETED/RENAMED) value from either side wins over a plain default ACTIVE from the other, since only `GitAdapter` ever observes lifecycle and ACTIVE-by-default carries no information; proven order-independent (informative side may be either the first- or second-processed entity). `source_location` — first non-`None` wins (deterministic tie-break for a case no current provider pair actually produces two different locations for one entity — documented, not exercised by real data).

**`IngestionPipeline` integration:** `_commit_entities` now re-resolves the full accumulated entity set (previous + this batch) through `resolve_entities()` on every commit — O(N) per call (not O(N²): `resolve_entities` itself is a single dict-keyed pass), an accepted V1-scale cost per the directive's own "do not prematurely optimize without measurements" (§28). Returns a raw-id → resolved-id map; `_commit_evidence` now remaps `Evidence.subject`/`.object` through this map **before** keying `CanonicalRelationship`s (the stored `Evidence` record's own `subject`/`object` fields are never mutated — only the relationship key uses resolved ids), so a normalized-path merge that renames a raw provider id never leaves a relationship dangling on the old one. Proven end-to-end by `test_entity_resolution_converges_differently_formatted_paths_through_the_pipeline` (`tests/test_ingestion_pipeline.py`): two fake providers report the same real file with a canonical and a `./`-prefixed path; the pipeline resolves to one FILE entity, and the second provider's relationship evidence attaches to the *canonical* id, not the raw one.

**Graph version behavior (directive Phase B §13):** unaffected — `resolve_entities()` is a pure function of static entity fields (never mutates a previously-published `GraphVersion`); `IngestionPipeline._materialize_store()` still builds a fresh, immutable store/version per `run()` from the accumulator's state at that moment, exactly as D4 already established. No change to that invariant was needed.

**Tests:** 23 new tests in `tests/test_entity_resolution.py` (path normalization ×5, exact/cross-provider FILE convergence ×2, normalized-path convergence + order-independence ×3, non-merge cases — different directory/base-type/revision ×3, symbol-entity non-renormalization honesty ×1, external-library convergence + version-significance ×2, provenance preservation — provider_ids/roles/lifecycle ×4, source_location tie-break ×1, empty/single-entity edge cases ×2), plus 1 new `IngestionPipeline` integration test. 311 tests total project-wide, 100% coverage on `codex/resolution/`, clean ruff/mypy. `CanonicalRelationship` gained a `contradiction_score: float` field (default `0.0`, backward compatible) in `codex/evidence/model.py`, added now because Reconciliation (§N) needs somewhere to store TAD §38's formula output — not otherwise used by this phase.

No new ADR — this closes TAD component #7's Entity Resolution half using signals the architecture (canonical id hashing, `provider_ids`) already establishes; no genuinely new architectural decision was required. No cross-document contradiction found. D1/D2/D3/D5/D6 untouched; D4's `_commit_entities`/`_commit_relationships` were changed, justified by the concrete defect found above, not as an unrelated contract change.

## N. Evidence Reconciliation — 2026-08-31

Per the post-D7 directive's Phase C. Closes TAD component #7's second half.

**A genuine finding, flagged rather than silently resolved (directive Rule 0.2):** the directive's own §15 ("Reconciliation Status Taxonomy") states the canonical taxonomy is "`VERIFIED/PARTIALLY_VERIFIED/QUALIFIED/DISPUTED/INCONCLUSIVE/REJECTED`." Direct inspection of `docs/TAD.md` shows this is **not** the enum that governs `CanonicalRelationship.status` — that field's type is `EvidenceStatus` (TAD §18, `SUPPORTED/WEAKLY_SUPPORTED/DISPUTED/UNRESOLVED/CONTRADICTED/UNSUPPORTED`), already implemented since Phase 1 and closed. The six-value list the directive names is TAD §50's, a **different, later-stage** taxonomy for the Verification Engine's answer/claim-level output (component #9/DTD-05, downstream of LLM synthesis) — confirmed by reading both enum definitions directly (TAD line ~539 vs. line ~1338), not assumed. TAD is internally consistent here (two distinct, correctly section-scoped enums, with an existing C-3-reconciled mapping between them); the conflation is only in the directive's own paraphrase, not a genuine cross-document contradiction, so this did **not** trigger a STOP (directive §32 condition #5/#7 requires an actual contradiction between authoritative documents, and none exists). Resolved by using `EvidenceStatus` — TAD §18's own, purpose-built field — for this phase, and leaving TAD §50's taxonomy untouched and out of scope (correctly deferred to the not-yet-built Verification Engine, per the directive's own §23 instruction not to implement it prematurely).

**Pre-audit findings (directive Phase C §14):**

- `CanonicalRelationship.supporting_evidence_ids`/`.contradicting_evidence_ids` already exist (TAD §73) — populated, not invented.
- `Evidence.effective_independence_group` (TAD §16) already correctly implements "omitted group defaults to non-independent *within the same provider*" (`provider_default:{provider}` — different providers get different default groups, i.e. independent by default, matching TAD §16's own two-part text: `independence_group = provider_default_family`, "if omitted, SHALL be treated as non-independent"). Reused as-is.
- **`provider_authority` (TAD §38's own formula input) has no defined source anywhere in HLRD/TAD** — the same class of gap ADR-018 already resolved for `evidence_quality`/`cost_factor` (TAD §31). Resolved the same way (explicit, `[0,1]`-normalized, caller-supplied) but **not** added to `codex.registry.scoring.ProviderScoreProfile` — that type is scoped to TAD §31's formula and closed (D2/ADR-018); extending it would force every existing D2/D3/D5/D6 test that constructs one to pass a new field it has no reason to care about. Instead, `IngestionPipeline` gained its own `provider_authority: Mapping[str, float] | None` constructor parameter, defaulting missing entries to full trust (`1.0`) rather than raising — deliberately different from ADR-018's "no default" choice, because this factor weights *confidence* on an already-committed relationship rather than *selecting* a provider, so silently under-trusting an unconfigured provider would be a worse default than full trust, and this choice keeps every pre-existing test passing unmodified.
- **No negation mechanism exists anywhere in the ontology.** `RelationshipType` has no "does-not-X" counterpart, and `Evidence` has no boolean/flag for asserting a negative fact — confirmed by inspecting all three real adapters' `RelationshipType` usage (D5/D6 closure audits, §J). The directive's own DISPUTED example ("SCIP → CALLS, Provider-X → DOES_NOT_CALL") is therefore **not representable** by any current provider. This is an intentional, documented limitation, not a silent gap: the algorithm implements the full TAD §38 formula and all six `EvidenceStatus` values generically (proven with handcrafted evidence in `tests/test_reconciler.py`), but `IngestionPipeline._reconcile_relationships` always calls it with `contradicting=()` in production, since there is no deterministic signal available to populate it without inventing one — `DISPUTED`/`CONTRADICTED`/`UNSUPPORTED` are correct-by-construction but not reachable end-to-end with Git/SCIP/CodeQL today.

**Algorithm (`codex.reconciliation.reconciler.reconcile_relationship`):** a relationship whose subject or object isn't a currently-resolved entity is `UNRESOLVED` (checked first — directive §19-20's "missing target is an information/system gap, not a dispute"). Otherwise: `weight = evidence.confidence × provider_authority × freshness_decay` (the freshness term reuses D2/ADR-018's already-established `default_freshness_score`, directly addressing directive §17/§22's "stale evidence affects confidence" — not reinvented). `contradiction_score = Σcontradict_weight / (Σsupport_weight + Σcontradict_weight)`, exactly TAD §38's literal formula (verified against the arithmetic in a dedicated test, not just direction). Confidence combines *supporting* evidence with an independence-aware rule: same-`effective_independence_group` records collapse to their single highest weight first (no double-counting correlated evidence — directive §16/§22), independent groups combine via `1 - Π(1 - weight)` (a standard, deterministic probability-combination rule — not a learned/probabilistic *identity* mechanism, which is what the "no probabilistic matching" prohibition in directive §8 targets for Entity Resolution specifically). Status: both supporting and contradicting present → `DISPUTED` (or `CONTRADICTED` if contradiction dominates, `contradiction_score >= 0.5`, a documented calibration point, not derived from HLRD/TAD, mirroring ADR-018's own framing of its freshness half-life); contradicting-only → `UNSUPPORTED`; supporting-only → `SUPPORTED` (support weight `>= 0.5`, same calibration-point status) or `WEAKLY_SUPPORTED`; neither → `UNRESOLVED`.

**`IngestionPipeline` integration:** a new `_reconcile_relationships()` step runs once per `run()`, after all providers commit and before `_publish()`, recomputing every accumulated relationship's `status`/`confidence`/`contradiction_score` from its full `Evidence` records (fetched from the `EvidenceStore` by id) against the current resolved entity set — not incrementally per evidence commit, so a relationship's status always reflects everything known about it at publish time, consistent with D4's "one new, immutable, published `GraphVersion` per `run()`" model. Two pre-existing tests' assertions were updated to match the now-real behavior (`tests/test_ingestion_pipeline.py::test_multiple_providers_contradictory_evidence_all_preserved`'s stale comment "No Reconciliation Engine exists yet" replaced with the actual reason its relationship stays `UNRESOLVED` — its fake providers never report entities, so the relationship's endpoints are genuinely unknown, not merely unreconciled; `tests/test_codeql_adapter.py::test_contradictory_evidence_between_git_and_codeql_both_preserved`'s obsolete `UNRESOLVED` assertion replaced with `SUPPORTED`/`WEAKLY_SUPPORTED`, matching what Reconciliation now correctly computes from real Git+CodeQL evidence).

**Tests:** 16 new tests in `tests/test_reconciler.py` (missing-target → `UNRESOLVED` ×3, single-provider support ×2, independent-vs-correlated confidence combination ×4, support+contradiction → `DISPUTED`/`CONTRADICTED`/`UNSUPPORTED` ×3, exact TAD §38 formula verification ×1, provider-failure-never-contradicts ×1, staleness reduces confidence ×1, provenance preservation ×1), plus 2 new `IngestionPipeline` integration tests (real `SUPPORTED` status through the pipeline; `provider_authority` constructor parameter proven to reach the Reconciler). 329 tests total project-wide, 100% coverage on `codex/reconciliation/` and `codex/ingestion/pipeline.py`, clean ruff/mypy.

No new ADR — `provider_authority`'s sourcing gap is resolved the same way ADR-018 already established the pattern for, not a new architectural decision. No cross-document contradiction found in the authoritative documents themselves (only in the directive's own paraphrase, addressed above). D1/D2/D3/D5/D6 untouched; D4's `run()` gained one new step (`_reconcile_relationships`) and its constructor gained one new optional parameter — additive, not a breaking contract change, confirmed by all pre-existing tests passing with at most a comment/assertion update reflecting genuinely new (and correct) behavior, never a workaround.

- **Budget cost estimation (Part 7):** TAD §41 gives the token-budget formula explicitly (`max_nodes = min(100, token_budget/average_node_cost)`, `max_edges = min(250, token_budget/average_edge_cost)`) but never defines `average_node_cost`/`average_edge_cost` numerically — again a formula-given/constants-missing gap, resolved as a documented calibration point. **Latency budget has no analogous formula anywhere in TAD** (§32 only describes the five-step pruning *procedure*, never how a plan's latency cost is estimated) — the only defensible non-inventive option that still lets `latency_budget_ms` function as an independent, testable budget (TAD §32 explicitly lists it as a co-equal Planner input) is to extend the *identical* average-cost-per-unit pattern TAD already specifies for tokens, with its own separately labeled calibration constants (`DEFAULT_AVERAGE_NODE_LATENCY_MS`, `DEFAULT_AVERAGE_EDGE_LATENCY_MS`). This is the single most judgment-laden call in this audit — flagged explicitly rather than silently applied; it is structural reuse of TAD's own specified pattern, not an unrelated invented cost model (e.g. no real wall-clock profiling or ML cost prediction), and remains fully swappable. **Not a STOP** under this reasoning, but recorded with maximum visibility for review.
- **Completeness percentage denominator (Part 8):** re-checked `docs/TAD.md` §33 directly — still gives only the four named thresholds (`LOW ≥50%, MEDIUM ≥75%, HIGH ≥90%, EXHAUSTIVE 100%+complete repository coverage`) with **no definition of what the percentage measures**. For `LOW`/`MEDIUM`/`HIGH`, TAD §32's own pruning rule ("Exhaustive queries cannot be pruned below required coverage") implies these three levels are the ones *eligible* for budget pruning — D9 only needs to know *which* level was requested (already available as an enum) to decide whether pruning is permitted at all, never to compute a numeric satisfaction percentage. Retrieval's stop condition for all four levels uses HLRD §39's qualitative rule (stop when coverage requirement satisfied, or no further expected value, or providers exhausted) implemented via `codex.coverage.classify_capability_coverage()`'s deterministic AND-gate, not a percentage. **Recorded per the directive's own instruction: "OPEN — DEFERRED TO CALIBRATION," not blocking D9, not falsely marked closed.**

No genuine HLRD↔TAD contradiction found. No QueryContract field conflict. No requirement forcing D7/D8 to be reopened.

### R.3 Graph version lock verification (Part 4)

Direct inspection of `codex.graph.version.GraphVersion` and `codex.graph.{store,memory_store}` confirms the lock is safe **by construction**, requiring no new concurrency primitive: `GraphVersion` is immutable once `.published` (already enforced, `.publish()` returns a copy); `InMemoryGraphStore.__init__(self, version: GraphVersion)` binds exactly one immutable version to exactly one store instance for its entire lifetime — there is no method anywhere on `GraphReader`/`GraphStore` that could change `.version` after construction, and `IngestionPipeline.run()` (D4, unmodified) always materializes a **new** `InMemoryGraphStore` instance per call rather than mutating a previously returned one (already proven by D4's own tests: "a previously returned result is never mutated, including by a later failing run"). Therefore: **as long as the Planner and the Retrieval Engine share the exact same `GraphReader` object reference for the lifetime of one query, "silently switching versions" is structurally impossible** — there is no second version for it to switch to. No STOP; no invented locking/concurrency semantics needed.

One real, load-bearing gap found and resolved (not a STOP): **there is no "current/latest GraphReader for repository X" registry anywhere in the codebase** — `IngestionPipeline.run()` returns a fresh `IngestionResult`/`GraphStore` to its immediate caller and nothing persists a "latest version" mapping. TAD's own 18-component list has no "Graph Version Registry" component either — obtaining "the current graph for this query's repository" is an orchestration-layer concern that sits **above** the Planner (and above D9's scope), consistent with how every other cross-cutting dependency in this codebase is supplied (D1's `ProviderAdapter`, D2's `CapabilityRegistry` — all constructor/call-parameter injected, nothing globally looked up). **Resolved as an implementation detail (category 1): `plan_query()`'s public signature takes an already-selected `GraphReader` and the `IngestionResult` that produced it as explicit parameters** — the Planner's job per TAD §20 is only to *lock* (capture `.version` from) whatever reader it is handed, not to search for one. `CONCURRENT_UPDATE_DETECTED` telemetry (TAD §55) is recorded when a caller later re-invokes retrieval against a *different* `GraphReader.version.version_id` for the same in-flight `RetrievalPlan` — detectable structurally by comparing the locked `version_id` against whatever reader retrieval is actually asked to run against, with no external locking system required.

### R.4 Provider selection boundary (Part 5)

`codex.registry.registry.CapabilityRegistry.rank(capability, repository, *, now=None)` (D2, ADR-018-closed) already implements exactly the query-time ranking behavior TAD §31 specifies — ties broken deterministically by `provider_name`, `capability_match=0` exclusion built in via `providers_for()`. **D9 calls `rank()`/`providers_for()` directly and does not reimplement any scoring.** The ingestion-time/query-time distinction is preserved unmodified: `IngestionPipeline` (D4, untouched) still runs every usable provider so contradictory evidence reaches the graph; D9's provider selection only decides which already-ingested provider's evidence to *prioritize when ranking retrieved evidence*, never which provider gets to write to the graph — those are genuinely separate operations on separate objects (`CapabilityRegistry.evaluate()`-driven ingestion vs. `CapabilityRegistry.rank()`-driven retrieval-time preference), not collapsed.

### R.5 Retrieval execution (Part 11) — the one additive gap

Direct inspection of `codex.graph.store.GraphReader` confirms it exposes only `get_entity(canonical_id)`, `get_relationships(...)`, and `neighbors(canonical_id, ...)` — **no method exists to look up an entity by name/qualified_name, and no method enumerates all entities**. This blocks the single most basic retrieval operation TAD §35 itself lists ("entity lookup") and HLRD §33 requires ("Candidate Generation... Graph" as a source): turning `QueryContract.targets: list[str]` (free-text strings like `"authenticate"`) into starting graph entities is otherwise impossible through the existing interface. No prior D1-D8 component ever needed this (D1-D4 only *write*; D5-D8 never read the graph at all), so this was never previously discovered.

**Resolved as an additive, non-breaking extension, not a STOP and not a modification of existing D1-D8 behavior:** one new read-only method, `find_entities(*, name=None, qualified_name=None, base_type=None) -> list[RepositorySymbol]`, added to the `GraphReader` Protocol and implemented in `InMemoryGraphStore` (exact/substring string matching only — no embeddings, no fuzzy matching, fully deterministic, consistent with HLRD §34's "embeddings are optional... SHALL NOT become prerequisites"). `InMemoryGraphStore` is the only concrete implementer anywhere in the codebase (confirmed by direct search), so this is purely additive — no existing caller's behavior changes, no existing test needs updating. Documented here with maximum visibility per the "no silent architectural decisions" rule, exactly like D4's evidence-discard-bug fix and D8's `required_evidence` mapping-table addition were.

### T.5 Phase E — D10 Security Boundary Audit

No D10 code exists yet to AST-audit directly (`codex.llm`/`codex.verification` do not exist in the codebase — confirmed by directory listing). This section states the invariants D10's eventual implementation must satisfy, each traced to its authoritative source and to the existing precedent that already enforces the analogous invariant one layer up:

- **Repository text is untrusted data** — HLRD §41 ("LLM SHALL NOT be treated as an authoritative source of repository truth"); precedent already set by D8's `QueryContract` security tests (`test_qu_security.py`: user query text never modifies structured fields) and D9's boundary tests.
- **EvidencePackage is data, not instructions** — TAD §43 ("LLM receives Query + EvidencePackage + ResponseContract... does not receive unrestricted repository access"); D10 must construct the LLM prompt so that every EvidencePackage field (entity names, evidence text, source locations — all ultimately repository-derived strings) is passed as data content, never concatenated into instruction-bearing prompt segments the model could be steered by.
- **Retrieved source code cannot override system/developer policy** — same principle, applies specifically to `EvidencePackage.source_context` (`RepositorySymbol.source_location`-bearing entities) once real source-snippet retrieval is added (currently deferred, §S.C) — repository file content is exactly the class of string HLRD §41 forbids treating as authoritative.
- **Repository comments/docstrings cannot instruct the LLM to ignore verification** — same as above; also structurally reinforced by the fact that Verification (TAD §46-47) is deterministic and runs *after* the LLM call, over the LLM's own structured claims against the (separately, deterministically retrieved) evidence — a comment cannot talk its way past a check it never participates in.
- **LLM output cannot modify EvidencePackage** — architectural: `EvidencePackage` is D9's output, constructed before the LLM is ever invoked (TAD §43's own input ordering); D10 must not design any mutation path from LLM response back into the package.
- **LLM output cannot modify GraphVersion** — same; `GraphVersion` is locked by D9 (T.1 item 2) before D10 exists in the call chain; D10 must only *read* `EvidencePackage.graph_version`, never construct or request a new one.
- **LLM output cannot create evidence** — architectural: `Evidence` records only ever originate from `ProviderAdapter.normalize()` (D1) via `IngestionPipeline` (D4); D10's claims are typed `{subject, predicate, object, claim_type}` (TAD §45), never an `Evidence`-shaped object, and must never be upserted into `EvidenceStore`/`GraphStore`.
- **LLM output cannot promote a claim to VERIFIED** — TAD §46's own pipeline ordering (claim extraction → ... → confidence → answer decision) places verification-state assignment strictly after and independent of the LLM call; the LLM's own `claim_type` field (`FACT`/`DERIVED`/`INFERENCE`/`UNKNOWN`, TAD §45) is the model's *claim about itself*, never the verification verdict — D10 must keep these two enums structurally separate (also T.4 item 2's naming-collision discipline).
- **Verification is deterministic and authoritative over LLM assertions** — TAD §47 ("Complex semantic assertions default to UNRESOLVED unless deterministic rules exist") and HLRD §41 (Verification Layer as "the enforcement mechanism against hallucination") both state this directly.
- **The LLM cannot choose files/providers/evidence outside the supplied EvidencePackage** — TAD §43's closed input list (`Query + EvidencePackage + ResponseContract`) and the already-established Planner precedent (TAD §30, D9 §R.4: "the planner determines retrieval scope... never asks 'what files should I look at?'") extends identically to the LLM Gateway: it receives a pre-selected, bounded package and has no tool-call/file-access surface in V1's design (TAD §43 lists no such capability).
- **The planner cannot ask the LLM which files to inspect** — already true and tested today (D9 §R.11, `test_no_llm_or_slm_model_dependency_imported`, `test_no_module_imports_forbidden_dependencies`); re-confirmed as still true with no code change in this audit phase.
- **The verifier cannot ask the LLM whether its own claim is true** — TAD §47's deterministic-only entailment list contains no LLM invocation; TAD §46's pipeline diagram never routes back to the LLM Gateway from Verification except via the single explicit RE-SYNTHESIZE path (§49), which asks for a *new answer*, not a self-judgment of the old one.

No violation exists today (no D10 code exists). Every invariant traces to an authoritative source or an already-enforced precedent one layer up. **D10.9 (security/boundary tests) must include an AST-based import-boundary test for `codex.llm`/`codex.verification` matching the `codex.planner`/`codex.query_understanding` precedent, plus a prompt-construction test proving EvidencePackage content is never string-concatenated into a system/instruction-role prompt segment.**

### T.7 Open Architectural Decisions

1. **Contradiction-penalty numeric thresholds** (T.3 item 4) — TAD §48 gives only qualitative "significant"/"weak" language; the directive's `>0.6`/`<0.4` values are not found in any authoritative document. **Recommendation**: resolve as a documented calibration point at D10.4/D10.5 time, following the exact ADR-018/D8-decay/D9-ranking-weight precedent (a clearly-labeled, swappable default, not a claimed-final value) — `0.6`/`0.4` are reasonable defaults consistent with the directive's stated intent and can be adopted as such **if the user confirms this is acceptable**, rather than silently invented.
2. **Re-synthesis counter interaction** (T.4 items 9/11) — does the schema-invalid path (TAD §44) and the contradiction path (TAD §49) share one global "maximum 1 re-synthesis" counter, or does each failure class get its own budget of 1? **Recommendation**: a single shared counter (one re-synthesis attempt total per answer, regardless of trigger reason) is the more conservative, TAD-consistent reading (TAD §49 says "Maximum V1 re-synthesis: 1" without qualifying it per failure type), and avoids an unbounded-retry loop where a malformed-then-contradicted-then-malformed-again cycle could otherwise consume multiple LLM calls.
3. **`ResponseContract`'s exact structure** (T.2) — TAD §43 names it as an LLM Gateway input but never defines its fields separately from §44's `{answer, claims[]}` schema. **Recommendation**: treat `ResponseContract` as the formal JSON Schema descriptor whose required shape TAD §44 already gives (i.e., the schema-as-artifact the Gateway constructs and passes to constrain generation) — not a new, additional structure.
4. **`EvidencePackage.evidence` should also resolve `contradicting_evidence_ids`** (T.1 item 11) — recommended as a small, non-blocking D9 addendum (or D10.2 prerequisite step) so the package is self-sufficient per TAD §42.

None of these four require an ADR (no genuine cross-document architectural conflict); all are calibration-point or interpretation-level decisions in the same class already resolved repeatedly throughout D1-D9, requiring only the user's confirmation before D10 code encodes them.
