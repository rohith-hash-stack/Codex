## Two material findings from this pass

1. **CodeQL's licensing is not permissive for arbitrary repositories.** Free use is scoped to public/open-source analysis or academic research; private-repo analysis requires a commercial GHAS license. This is now a concrete input to ADR-005 and to how the Capability Registry should represent CodeQL's availability per-repository, not just per-installation.
2. **`SillySerpent/Repograph` is AGPL-3.0.** Codex's existing "reuse the idea, not the code" stance toward that project (recorded in `docs/research/provider-formats.md` and `docs/architecture-conformance-audit.md`) turns out to be a license requirement, not just a caution — vendoring or wrapping that code would obligate Codex to AGPL-3.0 terms.

Neither finding blocks the next implementation steps (`ProviderAdapter` contract, Capability Registry, Git Adapter, ingestion pipeline, SCIP Adapter) — both matter once ADR-005 and ADR-006 are actually drafted.

## Third material finding — D7 (2026-08-31)

3. **All three candidate "at least one repository intelligence provider" sources (HLRD §8) have a real, blocking problem, not a preference-level one.** `SillySerpent/Repograph` is AGPL-3.0 *and* exposes no portable artifact (CLI/Python-API/MCP over an in-process Kuzu store only) — there is nothing safe to consume without either violating the license or reimplementing its entire pipeline. `chokevin/repograph` is MIT (no license obstacle) but its one capability Codex doesn't already have from Git+SCIP+CodeQL — `calls`/`references`/`inherits` edges — is built by a sub-2-second tree-sitter pipeline with no documented type/semantic resolution, the same shallow-syntax profile D5's own research already showed is insufficient to deterministically distinguish a call from a bare reference; adopting it would mean putting an undemonstrated-determinism relationship into the canonical graph. **Sourcegraph** remains genuinely un-researchable from this environment (`sourcegraph.com` still returns a connection failure, not just a slow response) and would in any case require either a live external API dependency or a full self-hosted deployment — a materially different, heavier input-contract shape than every adapter built so far. This blocks D7 as a genuine architectural gate (`docs/architecture-conformance-audit.md`'s §K) rather than an implementation detail to route around.

## Fourth material finding — Gap A closure, SCIP's "." placeholder (2026-08-31)

4. **SCIP's `"."` empty-`Package`-field placeholder has confirmed, documented semantics — it means "unset," not a literal period.** `scip.proto`'s `Package` message itself carries no comment about this (re-fetched directly, confirmed empty), but the reference `scip` Rust crate's `bindings/rust/src/symbol.rs` (`raw.githubusercontent.com/sourcegraph/scip/main/bindings/rust/src/symbol.rs`, fetched directly — read only for its documented format/parse *behavior*, never copied, per `docs/policy-external-references.md`) settles it definitively: `format_symbol` emits literal `"."` for any `manager`/`name`/`version` that is empty or when `Package` itself is absent (a space-separated symbol string can't otherwise represent an empty token), and that same crate's own `parse_symbol` converts a `"."` token straight back to `""` via a small `dot()` helper — round-tripped and proven by the crate's own test suite (`formats_symbol_with_dots`: a Package-less symbol serializes to `"scip-ctags . . . foo."` and parses back to three empty fields). **Resolution:** `codex.provider.scip.mapping.parse_symbol()` now normalizes `"."` → `""` for `manager`/`package_name`/`package_version` before Codex ever builds an `EXTERNAL_LIBRARY` `qualified_name` from them — a real, previously-undiscovered defect (the literal `"."` would otherwise leak into Codex's own canonical identity strings, e.g. `".:foo@1.0"`, misrepresenting an unset field as a manager literally named `"."`) fixed with 5 new tests (`tests/test_scip_mapping.py`, `tests/test_scip_adapter.py`) — not previously verified against any real artifact or the reference implementation's own documented round-trip behavior. This does not affect in-repo symbol identity (locally-defined symbols use `descriptor_path`, never `manager`/`name`/`version`) — only `EXTERNAL_LIBRARY` identity, where it now produces a semantically correct (if visually unusual, e.g. `":unmanaged-pkg@"`) identity instead of a misleading one.

## Fifth material finding — FND-1 fix cycle, SCIP's `enclosing_symbol` field (2026-09-02)

5. **`SymbolInformation.enclosing_symbol` (`scip.proto` field 8) exists specifically to solve FND-1's problem, but real `scip-python@0.6.6` output never populates it — confirmed by direct wire-level inspection, not assumed.** The schema's own comment (re-fetched directly from `raw.githubusercontent.com/sourcegraph/scip/main/scip.proto`) is explicit: "if you want to know the 'parent' or 'owner' of this local symbol... use `enclosing_symbol` to locate it" — precisely the "which real entity does this locally-scoped/nested symbol belong to" question FND-1 raises. Before designing any fix, `codex.provider.scip.wire.parse_fields()` was used to inspect the **raw** `SymbolInformation` submessages for a confirmed FND-1 collision (django's `AbstractBaseUser#setter()`, both real `check_password`/`acheck_password`-nested closures) directly, bypassing the higher-level decoder: only wire fields `1` (symbol) and `3` (documentation) are present on either `SymbolInformation` entry — field `8` is absent from the raw bytes entirely, on both. This rules out "Codex's decoder is silently dropping it" (the decoder didn't decode field 8 *at all* before this pass) and confirms the gap is upstream, in this specific indexer version's own output, not a Codex defect. **Resolution:** `codex.provider.scip.index.ScipSymbolInformation` now decodes field 8 into a new `enclosing_symbol: str = ""` attribute, for completeness and forward-compatibility with any future `scip-python` version (or other SCIP producer) that does populate it — but the FND-1 fix itself (`codex.provider.scip_adapter._nested_symbol_disambiguation`) does **not** branch on it, since there is no real data to exercise or validate that branch against (adding untested, unexercised logic for data a producer never emits was judged worse than a clearly-documented known limitation). The operative mechanism instead uses each occurrence's own source **position** — the nearest textually-preceding real (non-local, non-Parameter) symbol definition in the same document — as the deterministic proxy for enclosing scope, since SCIP's own `Occurrence.range` (unlike `SymbolInformation`, which carries no location at all) *is* reliably present. Two adjacent research questions were also answered directly rather than assumed: **`AstCallsAdapter`'s existing `_DefinitionCollector`** (re-read directly, `src/codex/provider/ast_calls_adapter.py`) tracks only two lexical levels — `self.functions` (module-level `FunctionDef`) and `self.methods` (keyed by `(class_name, method_name)`, one level of class-nesting) — with no recursion into a function/method's own body, so it independently corroborates the same gap: neither provider currently has entity-level knowledge of nested closures at all (confirmed via real ingestion: `AbstractBaseUser#setter()`'s `provider_ids` carry only `{"scip": ...}`, never `"ast_calls"`, both before and after this fix). Extending it was considered and rejected for this cycle: SCIP-side disambiguation alone already satisfies the identity contract (distinct nested entities, distinct canonical IDs) without a second provider's cooperation, keeping the fix contained to one file/one provider, per the cycle's own minimality requirement.

## Sixth material finding — FND-1 fix cycle, a raw SCIP occurrence column is not indentation (2026-09-02)

6. **A confirmed real-data false negative, found by this fix's own exhaustive five-repository sweep, forced a second design correction: a SCIP occurrence's identifier-token *column* is not a safe proxy for true Python indentation, because different keyword prefixes (`def `, `async def `, `class `) shift a definition's identifier by different amounts even at identical real nesting depth.** The initial `_nested_symbol_disambiguation` design (position-based "nearest preceding container," per the fifth finding above) used each candidate container occurrence's own SCIP column directly. This passed 169/170 real cases across django/flask/click/pytest/requests, but the sweep's one remaining mismatch — django's `Signal.asend` (`django/dispatch/dispatcher.py`) — traced to a real, structural flaw, not a one-off: `Signal.send` is declared `def send(self, sender, **named):` (identifier column 8), while its ordinary top-level sibling `Signal.asend` is declared `async def asend(self, sender, **named):` (identifier column 14, six columns further right purely from the longer `async ` keyword). Both are genuine top-level `Signal` methods at the *same* true indentation (0 leading-whitespace columns before the keyword, in both cases), but a raw-column comparison (`8 < 14`) reads `send` as `asend`'s "enclosing container," silently mislabeling a real top-level method as one of two unrelated closures also named `asend` nested elsewhere in the same class. **Resolution:** `_nested_symbol_disambiguation`/`_nearest_preceding_container` now compare each candidate's *true source indentation* — the real leading-whitespace count read directly from the source file on disk (`_read_line_indentations`, a narrow, explicitly-scoped exception to this adapter's general "SCIP-index-only" design, reading the same source tree `scip-python` itself indexed, via `RepositoryMetadata.local_path` threaded through `extract()` → `_collect_definitions()` → `_nested_symbol_disambiguation()`) — falling back to the previous raw-column comparison (`_effective_indent`) only when the real source file cannot be read (moved, deleted, or — as in every handcrafted test fixture that predates this finding — never written to disk at all), matching this module's existing "never fabricate, degrade to the next-best deterministic signal" pattern rather than raising or silently disabling detection. Re-running the exhaustive five-repository sweep after this correction found **zero mismatches** across all five repositories (164/164 genuinely-split symbols verified, 515 total correctly-distinct disambiguated entities), including the corrected `Signal.asend`/`Signal.send`/`Signal.send_robust` three-way case, which now resolves to three distinct entities with three distinct canonical IDs — the real top-level `asend` method correctly keeps a plain (non-`<locals>`) identity and correctly converges with `AstCallsAdapter`'s own independently-tracked `Signal.asend` entity, exactly as directive D5 §9 intends. A dedicated regression test (`tests/test_scip_adapter.py::test_fnd1_true_indentation_not_fooled_by_keyword_length`) reproduces this exact keyword-length shape against a real, matching source file written to the test's own `tmp_path`, and a second test (`test_fnd1_no_real_source_file_falls_back_to_raw_column`) locks in the fallback path for when no real source file is available.

## Seventh material finding — FND-2 fix cycle, resolving a container to identity instead of matching its descriptor string (2026-09-02)

7. **FND-2's root cause, confirmed via direct re-reading of `_nested_symbol_disambiguation`/`_nearest_preceding_container` (`scip_adapter.py`) rather than assumed: the nearest-container search returns a container occurrence's own *descriptor string*, and `_nested_symbol_disambiguation` groups a nested symbol's occurrences by that string — correct only when a container's descriptor string is itself a reliable proxy for "which real scope instance this is."** It is not, in two confirmed, independently-reproduced shapes (`docs/python-fidelity-gap-register.md`'s FND-2 row, discovered by the prior cycle's independent `ast`-based audit, not by this fix): (a) a container itself genuinely nested in 2+ different real scopes (e.g. flask's `index()`, redefined once per test method) serializes to the *identical* descriptor in every instance — SCIP's descriptor grammar was already confirmed (Finding 5 above) to drop enclosing-function segments in exactly this situation — so every nested child's "nearest container" lookup returns the same string regardless of which real `index()` it is actually inside, collapsing genuinely distinct children into one group; (b) a container redefined *in place, within one real shared scope* (django's `Person`, redefined 4 times inside one test method — the ordinary GAP-13/14 pattern, confirmed to already converge correctly *for the container itself*) only carries a Definition-role SCIP occurrence on its *first* textual instance (GAP-13's own root cause, now confirmed to apply to classes as well as functions) — so a nested child's lookup, searching only Definition-role occurrences for "nearest preceding container," skips straight past the container's own later, un-marked re-declarations and lands on whatever unrelated sibling happens to be nearest in raw text position instead.

   **Research performed before any code change**, per this cycle's own mandatory research-first requirement:
   - **SCIP grammar / `enclosing_symbol`**: already established (Finding 5) and re-confirmed unpopulated by real `scip-python@0.6.6` output; not re-investigated, since nothing about FND-2 suggests this producer's behavior has changed. SCIP's `Occurrence.range` (position) remains the only reliably-present per-occurrence location data — there is no richer "scope chain" field anywhere in the wire format to consume instead.
   - **scip-python's internal symbol construction** (research/reference only, via its own public descriptor-grammar behavior observed empirically against real `.scip` output — no source code read, consistent with the clean-room policy): the tool's own *internal* Pyright-based type-checking pass necessarily has a fully correct enclosing-scope chain in memory (Pyright always resolves true lexical scope to type-check correctly) — but that information is **not serialized** into the descriptor string it emits; only the class-chain (and, conditionally, a pure-function chain — Finding 5/6) survives into the wire format. Confirms Codex cannot recover this from the artifact alone by any smarter *parsing* of the descriptor string — the information is genuinely discarded upstream, and any fix must be built from what Codex *can* independently reconstruct: real occurrence positions plus real source indentation (already read for FND-1, `_read_line_indentations`).
   - **CodeQL's lexical scope model** (research precedent only, per `docs/architecture-conformance-audit.md`'s D6/D7 findings — no CodeQL library or query code introduced): CodeQL's Python scope model represents `getEnclosingScope()` as an explicit graph edge from every scope to its immediate parent scope *object* (not by name) precisely because two lexically identical, differently-located scopes (e.g. two functions named `f` in two different modules) are not interchangeable — the parent relationship is always resolved to a specific scope *node*, never matched by re-deriving and comparing a name string. This is the architectural precedent this fix follows: identify a container by its own resolved position/identity in a containment tree, not by re-matching its descriptor text.
   - **RepoGraph** (research precedent only): its "contains" edges are likewise built as a parent→child hierarchy over concrete AST/tree-sitter nodes (by node identity), never by re-parsing a serialized name — the same precedent as CodeQL, independently confirming this is the standard shape for this kind of problem, not a Codex-specific invention.
   - **Research questions answered**: (1) yes — resolving the container to its own identity first, then deriving the child's identity from *that resolved identity* (not the container's raw descriptor string), is both sufficient and the design CodeQL/RepoGraph's own precedent supports. (2) Yes, deterministically, using real occurrence positions/indentation plus a recursive same-real-scope collapsing rule (below) — no `module → class → function → nested` level needs to be skipped or guessed. (3) An ambiguous immediate container is resolved *recursively* by the exact same mechanism, one level up — the fix does not special-case "container is ambiguous," it simply always resolves container identity before using it, at every depth. (4) A redefined container with multiple real textual instances resolves to **one shared identity** for all instances that share the same true real enclosing scope (GAP-13/14's own contract, preserved) — reached by collapsing same-descriptor, same-resolved-parent instances into one representative, using ALL of that container's real textual re-declaration positions (not only its lone Definition-role occurrence) to find them. (5) Yes: true source indentation (already read via `_read_line_indentations`) plus real occurrence *position* (not a bare line-number identity, but position used as one input to a resolved, recursively-collapsed scope identity) is sufficient and deterministic; no AST library is introduced — indentation and position are read directly from the existing `.scip` occurrences and the already-established source-read exception. (6) Yes — this fix reuses FND-1's exact indentation-reading machinery (`_read_line_indentations`/`_effective_indent`) unchanged, generalizing the *grouping key* `_nested_symbol_disambiguation` uses rather than adding a second, descriptor-specific patch alongside it. (7) Confirmed available-but-discarded: every real textual class/function re-declaration's own occurrence position (even when SCIP tags it `ReadAccess` instead of `Definition` for a redefined container) — Codex's existing container-candidate list only consumed Definition-role occurrences, silently discarding these. (8) Both confirmed FND-2 shapes are Codex identity loss, not a provider-boundary limitation: the raw position/occurrence data needed to resolve them correctly is present in the real `.scip` index in every reproduced case; scip-python's own descriptor-string limitation (Finding 5) is the *reason* the bug exists, but it is not itself a case where the needed information is absent from the artifact — only the derived answer is, until reconstructed from position.
