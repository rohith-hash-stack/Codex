Proven with 25 behavioral tests against a test-only `FakeProviderAdapter` (not a real provider), including a follow-up clarification: `health_status` (`ProviderHealthStatus`: HEALTHY/DEGRADED/UNHEALTHY/UNKNOWN) is the provider's own operational condition; `availability(capability, repository) -> float [0,1]` is a separate, adapter-reported readiness signal per capability/repository, structurally independent of health (tests prove a HEALTHY provider can report 0.0 availability and vice versa). 100% coverage on `codex.provider`.
9. **D2 — Capability Registry (done, ADR-018 resolved, see `codex.registry`):** `CapabilityRegistry` distinguishes a static "which providers declare capability X" lookup (`providers_for()`) from a live, per-repository evaluation (`evaluate()`/`rank()`) that classifies each candidate as `AVAILABLE`/`PARTIAL`/`UNAVAILABLE`/`INELIGIBLE`/`FAILED` by calling only the D1 contract's own methods — no provider-specific logic anywhere. `rank()` implements TAD §31's `ProviderScore` formula with the exact specified weights, sorts deterministically (score, then provider name), and excludes capability-mismatched providers before scoring, per spec. **ADR-018 (all 5 factor sources decided):** `capability_match`/`availability` Registry-derived; `evidence_quality`/`cost_factor` sourced from a `ProviderScoreProfile` attached once at `register()` — canonical, not per-query, so ranking is caller-independent; `freshness` Registry-derived from the adapter's timestamp via a documented default decay function (explicitly a calibration point, not a final algorithm). `rank()` now takes no caller-supplied scoring values at all.
10. **D3 — Git Adapter (done, see `codex.provider.git_adapter`):** the first concrete `ProviderAdapter`, built on `GitPython`. Exactly two capabilities, matching HLRD §13's stated Git scope: `HISTORY` (tip-commit diff, including the initial-commit empty-tree case, → `RepositorySymbol` entities carrying `lifecycle_status` ACTIVE/DELETED/RENAMED) and `CO_CHANGE` (bounded commit-window co-occurrence → `CO_CHANGED_WITH` evidence with saturation-based confidence). Total-provider failure (`ProviderExtractionError(UNAVAILABLE)`) is kept distinct from capability-level failure/timeout (lands in `EvidenceCohort.failed_capabilities`, never raises) per the D3 failure-semantics taxonomy. Security: argument-array-only GitPython calls, no `shell=True`, empirically confirmed no shell-injection risk. All 30 tests run against real temporary git repositories, never this repository's own history.
11. **D4 — Ingestion Pipeline (done, see `codex.ingestion`):** `IngestionPipeline` orchestrates `PROVIDERS -> INGESTION PIPELINE -> EVIDENCE NORMALIZATION -> CANONICAL GRAPH` (TAD §72-73, HLRD §23) with zero provider-specific logic — provider discovery/capability selection/eligibility all go through `CapabilityRegistry.evaluate()`. Each provider's extraction is isolated (a failure or unexpected exception never discards another provider's already-committed evidence); every evidence record for a given relationship triple is preserved in `CanonicalRelationship.supporting_evidence_ids` without adjudication, since the Reconciliation Engine doesn't exist yet. The pipeline accumulates entities/evidence per repository across calls rather than rescanning, and each `run()` produces one new, immutable, published `GraphVersion` with a deterministic `version_id`. Proven with 22 behavioral tests (19 fake-provider, 3 against the real `GitAdapter` in temporary git repos), 100% coverage.
12. **D5 — SCIP Adapter (done, see `codex.provider.scip_adapter`, `codex.provider.scip`):** the second concrete `ProviderAdapter`, built on an independently-written, dependency-free SCIP protobuf decoder (`codex.provider.scip.{wire,index,mapping}` — no `protobuf` package, nothing vendored/generated from `scip.proto`). Four capabilities determined and documented before coding: `SYMBOL_DEFINITION` (definitions → entities, base type via `Kind` or a descriptor-suffix fallback since real producers leave `kind` unset), `SYMBOL_REFERENCE` (references → `REFERENCES`/`IMPORTS` evidence), `IMPLEMENTATION` (`is_implementation` → `IMPLEMENTS`), `TYPE_RELATIONSHIP` (`is_type_definition` → `REFERENCES`). `CALL_RELATIONSHIP`/`EXTENDS` deliberately not produced — real SCIP output has no deterministic signal for either (confirmed against a real `scip-typescript`-generated artifact, not assumed). External symbols become `EXTERNAL_LIBRARY` entities with revision-independent, package-qualified identity; FILE entities converge with `GitAdapter`'s via the same `build_canonical_id` call. Proven with 99 SCIP-specific behavioral tests, 100% coverage on all four new modules, including malformed-input, failure-isolation, determinism/idempotency, and real-artifact tests, two of them running SCIPAdapter through the unmodified D4 `IngestionPipeline`.
13. **D6 — CodeQL Adapter (done, see `codex.provider.codeql_adapter`):** the third concrete `ProviderAdapter`, one capability (`DATA_FLOW`), consuming a pre-generated SARIF 2.1.0 file only — never invokes the `codeql` CLI, never generates a CodeQL database. Determined before coding, per the directive's required capability/evidence mapping table (in the module's own docstring): a path-problem result (`codeFlows` with ≥2 distinct locations) → one `REFERENCES` `Evidence` record between the flow's source/sink FILE entities (Class B, deterministically derived); a plain "problem"-kind result (the majority of real CodeQL output) → a `codeql:finding:<ruleId>` role on the FILE entity, no fabricated `Evidence` record (`Evidence` needs two distinct endpoints a single-location finding doesn't have — a documented V1 limitation, not a workaround). `CALL_RELATIONSHIP`/`EXTENDS`/`IMPLEMENTS`/`DEPENDS_ON` deliberately never produced — no SARIF field asserts any of them, and the one field that could carry per-step semantics (`threadFlowLocation.kinds`) is optional, freeform, and unpopulated in every real fixture inspected. The CodeQL CLI's own Terms and Conditions (fetched and read directly) restrict free use to academic research/OSS analysis, requiring a paid GHAS license for private-repo automation — resolved by applying D5's already-precedented "consume, don't generate" pattern rather than triggering a STOP. Validated against six real SARIF artifacts from `github/codeql-action`'s own test suite plus two handcrafted fixtures; surfaced and fixed two more real bugs (a `results`-key omission wrongly treated as malformed; a non-conforming `artifactLocation.uri` wrongly accepted as a file path) and one design bug (mixed per-run success/failure collapsed into false full success, fixed with a three-way `successful`/`failed`/`partial` classification). 45 new behavioral tests, 100% coverage on `codeql_adapter.py`, including coexistence with Git and SCIP evidence and contradictory-evidence preservation through the unmodified D4 `IngestionPipeline`.
