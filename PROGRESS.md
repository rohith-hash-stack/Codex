3. **Phase 1 — Foundation (TAD §80): in progress.** Scaffolded as a Python project (`pyproject.toml`, `ruff`/`mypy`/`pytest`, GitHub Actions CI) with four modules under `src/codex/`:
   - `ontology/` — `BaseEntityType`, `CommonRole`, `RelationshipType`, `RepositorySymbol`, `SourceLocation`, and `build_canonical_id()` (HLRD §16-18, TAD §12-14).
   - `evidence/` — `Evidence`, `EvidenceCohort`, `EvidenceStatus`, `CoverageStatus`, `CanonicalRelationship`, and an `InMemoryEvidenceStore` behind an `EvidenceStore` protocol (TAD §15-18).
   - `graph/` — `GraphVersion`, and `GraphReader`/`GraphStore` protocols with a NetworkX-backed `InMemoryGraphStore` (TAD §12, §19-20, §53, §62).
   - `repository/` — `RepositoryManager` (register/clone, HEAD revision, changed-file detection between revisions) and its models (TAD §7, §72).

   17 tests pass; `ruff` and `mypy` are clean. Storage/provider technology is still whatever the in-memory Phase 1 defaults are — no ADR has selected a real backend yet (deliberate, per TAD §77).
4. **Provider format research (done, see [docs/research/provider-formats.md](research/provider-formats.md)):** pulled the real SCIP protobuf schema, CodeQL's SARIF v2.1.0 output shape, and both HLRD-referenced RepoGraph reference implementations before writing any adapter code — so adapter contracts match reality instead of guesses. Notable findings: SCIP gives no direct call edges (must be derived from occurrence roles + enclosing ranges); CodeQL's single-entity `problem` findings don't fit the `subject/predicate/object` evidence shape as cleanly as its `path-problem` data-flow queries do (flagged for ADR-005, not resolved); `SillySerpent/Repograph` is architecturally the closest existing analog to Codex (Kuzu-backed graph store, git co-change coupling, static+runtime split, MCP server interface) and adds **Kuzu** as an ADR-001 storage candidate and **MCP** as an ADR-015 API candidate. Sourcegraph's own Code Navigation API docs were **not** reachable from this environment (egress-blocked) — still open before ADR-006.
5. **Architecture Conformance Audit (done, see [docs/architecture-conformance-audit.md](architecture-conformance-audit.md)):** re-read HLRD + TAD in full against the actual code/tests, built a requirement traceability matrix (4 IMPLEMENTED, 10 PARTIALLY_IMPLEMENTED, 9 NOT_IMPLEMENTED, 1 spec-level CONTRADICTED), classified all 17 TAD §77 ADR candidates (14 genuinely open, 2 — ADR-012/013 — actually already closed by TAD and should fold into ADR-001/002, not be reopened), and found 6 cross-document contradictions (**C-1** through **C-6**). Two of those (C-1, C-2) are places Phase 1 code already made a silent, undocumented choice that happened to be defensible — now recorded explicitly rather than left as drift. One (**C-3**) is serious: HLRD and TAD define **three different, unreconciled enumerations** of the final verification/answer state (4 values vs. 6 values vs. 3 pipeline buckets, no stated mapping) — this blocks Phase 9 (Verification Engine) until resolved and is flagged as needing an explicit human decision, not guessed at. Also flagged that "DTD-01..05" referenced throughout HLRD/TAD (and this directive) **do not exist as separate documents** — they're inline labels inside TAD only.
6. **Architecture Reconciliation (done, see [docs/architecture-reconciliation.md](architecture-reconciliation.md)):** resolved all three contradictions from the audit, with the resolutions written into the actual specification (not just tracked here). **C-1**: `TESTED_BY` is canonical (production code → test); HLRD §16 amended, no code change needed. **C-2**: generic `provider_versions: dict[str, str]` is canonical; TAD §19 amended to drop the named-provider struct, no code change needed. **C-3**: TAD §50's six-value taxonomy (`VERIFIED, PARTIALLY_VERIFIED, QUALIFIED, DISPUTED, INCONCLUSIVE, REJECTED`) is now explicitly the canonical *internal* verification model, with two tested mapping functions required when Phase 9 is built — one down to HLRD's four-value presentation label, one down to TAD §5's three-bucket pipeline routing view; both docs amended with the mapping tables. Also resolved: DTD-01..05 stay embedded in TAD as section ranges (mapping table recorded, no separate documents), and ADR-012/ADR-013 are now formally marked CLOSED/SUPERSEDED in TAD §77 itself. A new `docs/resources.md` external-resource ledger also surfaced two material license findings: **CodeQL's free tier doesn't cover private-repo analysis** (needs a GHAS license — affects ADR-005 and Capability Registry per-repo availability), and **`SillySerpent/Repograph` is AGPL-3.0** (confirms "reuse the idea, never the code" is a license requirement, not just a preference).
7. **Clean-room implementation policy adopted (see [docs/policy-external-references.md](policy-external-references.md)):** formalizes the process already followed for research so far — `Reference → Understand → Specify → Independently Implement → Test`, never `Reference → Copy → Modify → Integrate`. Binding on every future provider adapter: study public specs/behavior only, record the resource in `docs/resources.md`, design the Codex interface independently, never copy third-party source or tests, and STOP for an explicit license decision before incorporating any third-party code. Both license gates already on record (CodeQL private-repo restriction, `SillySerpent/Repograph`'s AGPL-3.0) are cited as worked examples of what this triggers.
8. **D1 — ProviderAdapter Contract (done and approved, see `codex.provider`):** the shared contract every future adapter (Git, SCIP, CodeQL, Sourcegraph/RepoGraph) will implement. `ProviderAdapter` is a `Protocol` (matching the existing `GraphStore`/`EvidenceStore` pattern) exposing identity/version/capabilities/health/availability/freshness plus `validate()`, `check_eligibility()`, `extract()`, `normalize()`. Deliberately scoped: eligibility is adapter-*reported* only — the Capability Registry's SUPPORTED/AVAILABLE/UNAVAILABLE/INELIGIBLE aggregation logic is D2's job, not built here. `extract()`/`normalize()` reuse Phase 1's `RepositoryMetadata`/`Evidence`/`EvidenceCohort`/`RepositorySymbol` directly. Proven with 25 behavioral tests against a test-only `FakeProviderAdapter` (not a real provider), including a follow-up clarification: `health_status` (`ProviderHealthStatus`: HEALTHY/DEGRADED/UNHEALTHY/UNKNOWN) is the provider's own operational condition; `availability(capability, repository) -> float [0,1]` is a separate, adapter-reported readiness signal per capability/repository, structurally independent of health (tests prove a HEALTHY provider can report 0.0 availability and vice versa). 100% coverage on `codex.provider`.
9. **D2 — Capability Registry (done, ADR-018 resolved, see `codex.registry`):** `CapabilityRegistry` distinguishes a static "which providers declare capability X" lookup (`providers_for()`) from a live, per-repository evaluation (`evaluate()`/`rank()`) that classifies each candidate as `AVAILABLE`/`PARTIAL`/`UNAVAILABLE`/`INELIGIBLE`/`FAILED` by calling only the D1 contract's own methods — no provider-specific logic anywhere. `rank()` implements TAD §31's `ProviderScore` formula with the exact specified weights, sorts deterministically (score, then provider name), and excludes capability-mismatched providers before scoring, per spec. **ADR-018 (all 5 factor sources decided):** `capability_match`/`availability` Registry-derived; `evidence_quality`/`cost_factor` sourced from a `ProviderScoreProfile` attached once at `register()` — canonical, not per-query, so ranking is caller-independent; `freshness` Registry-derived from the adapter's timestamp via a documented default decay function (explicitly a calibration point, not a final algorithm). `rank()` now takes no caller-supplied scoring values at all.
10. **D3 — Git Adapter (done, see `codex.provider.git_adapter`):** the first concrete `ProviderAdapter`, built on `GitPython`. Exactly two capabilities, matching HLRD §13's stated Git scope: `HISTORY` (tip-commit diff, including the initial-commit empty-tree case, → `RepositorySymbol` entities carrying `lifecycle_status` ACTIVE/DELETED/RENAMED) and `CO_CHANGE` (bounded commit-window co-occurrence → `CO_CHANGED_WITH` evidence with saturation-based confidence). Total-provider failure (`ProviderExtractionError(UNAVAILABLE)`) is kept distinct from capability-level failure/timeout (lands in `EvidenceCohort.failed_capabilities`, never raises) per the D3 failure-semantics taxonomy. Security: argument-array-only GitPython calls, no `shell=True`, empirically confirmed no shell-injection risk. All 30 tests run against real temporary git repositories, never this repository's own history.
11. **D4 — Ingestion Pipeline (done, see `codex.ingestion`):** `IngestionPipeline` orchestrates `PROVIDERS -> INGESTION PIPELINE -> EVIDENCE NORMALIZATION -> CANONICAL GRAPH` (TAD §72-73, HLRD §23) with zero provider-specific logic — provider discovery/capability selection/eligibility all go through `CapabilityRegistry.evaluate()`. Each provider's extraction is isolated (a failure or unexpected exception never discards another provider's already-committed evidence); every evidence record for a given relationship triple is preserved in `CanonicalRelationship.supporting_evidence_ids` without adjudication, since the Reconciliation Engine doesn't exist yet. The pipeline accumulates entities/evidence per repository across calls rather than rescanning, and each `run()` produces one new, immutable, published `GraphVersion` with a deterministic `version_id`. Proven with 22 behavioral tests (19 fake-provider, 3 against the real `GitAdapter` in temporary git repos), 100% coverage.
12. **D5 — SCIP Adapter (done, see `codex.provider.scip_adapter`, `codex.provider.scip`):** the second concrete `ProviderAdapter`, built on an independently-written, dependency-free SCIP protobuf decoder (`codex.provider.scip.{wire,index,mapping}` — no `protobuf` package, nothing vendored/generated from `scip.proto`). Four capabilities determined and documented before coding: `SYMBOL_DEFINITION` (definitions → entities, base type via `Kind` or a descriptor-suffix fallback since real producers leave `kind` unset), `SYMBOL_REFERENCE` (references → `REFERENCES`/`IMPORTS` evidence), `IMPLEMENTATION` (`is_implementation` → `IMPLEMENTS`), `TYPE_RELATIONSHIP` (`is_type_definition` → `REFERENCES`). `CALL_RELATIONSHIP`/`EXTENDS` deliberately not produced — real SCIP output has no deterministic signal for either (confirmed against a real `scip-typescript`-generated artifact, not assumed). External symbols become `EXTERNAL_LIBRARY` entities with revision-independent, package-qualified identity; FILE entities converge with `GitAdapter`'s via the same `build_canonical_id` call. Proven with 99 SCIP-specific behavioral tests, 100% coverage on all four new modules, including malformed-input, failure-isolation, determinism/idempotency, and real-artifact tests, two of them running SCIPAdapter through the unmodified D4 `IngestionPipeline`.
13. **D6 — CodeQL Adapter (done, see `codex.provider.codeql_adapter`):** the third concrete `ProviderAdapter`, one capability (`DATA_FLOW`), consuming a pre-generated SARIF 2.1.0 file only — never invokes the `codeql` CLI, never generates a CodeQL database. Determined before coding, per the directive's required capability/evidence mapping table (in the module's own docstring): a path-problem result (`codeFlows` with ≥2 distinct locations) → one `REFERENCES` `Evidence` record between the flow's source/sink FILE entities (Class B, deterministically derived); a plain "problem"-kind result (the majority of real CodeQL output) → a `codeql:finding:<ruleId>` role on the FILE entity, no fabricated `Evidence` record (`Evidence` needs two distinct endpoints a single-location finding doesn't have — a documented V1 limitation, not a workaround). `CALL_RELATIONSHIP`/`EXTENDS`/`IMPLEMENTS`/`DEPENDS_ON` deliberately never produced — no SARIF field asserts any of them, and the one field that could carry per-step semantics (`threadFlowLocation.kinds`) is optional, freeform, and unpopulated in every real fixture inspected. The CodeQL CLI's own Terms and Conditions (fetched and read directly) restrict free use to academic research/OSS analysis, requiring a paid GHAS license for private-repo automation — resolved by applying D5's already-precedented "consume, don't generate" pattern rather than triggering a STOP. Validated against six real SARIF artifacts from `github/codeql-action`'s own test suite plus two handcrafted fixtures; surfaced and fixed two more real bugs (a `results`-key omission wrongly treated as malformed; a non-conforming `artifactLocation.uri` wrongly accepted as a file path) and one design bug (mixed per-run success/failure collapsed into false full success, fixed with a three-way `successful`/`failed`/`partial` classification). 45 new behavioral tests, 100% coverage on `codeql_adapter.py`, including coexistence with Git and SCIP evidence and contradictory-evidence preservation through the unmodified D4 `IngestionPipeline`.
14. **Not yet started:** any further ADR, the remaining provider adapter (Sourcegraph/RepoGraph — D3/D5/D6 cover Git, SCIP, and CodeQL), Entity Resolution + Reconciliation Engine (precondition now met with three providers, but not built), DTD-02..05 (query understanding/planning/retrieval/verification), LLM Gateway, benchmark corpus, or deployment work.
